# 収益化・案件挿入エンジン (Revenue Engine) for セイリ部

記事の構成案やドラフトを読み込み、読者の悩みや文脈に最も適したアフィリエイト案件を選定し、Seiribu Voice（誠実な案内人）のトーンマナーに従って自然に挿入するワークフローです。

> [!IMPORTANT]
> **【AIへの重要指示：事前ロード】**
> 本ワークフローを起動されたAIは、PHASE 1 に入る前に以下のファイルを `view_file` で読み込むこと。
> 1. `.agents/workflows/article-output-format.md` — 記事の出力フォーマットルール。
> 2. `.agents/skills/seiribu-affiliate-case-selector/SKILL.md` — 案件選定の主軸となるスキル。案件評価、最新性の判定、ルーティング方針はこれに従う。
> 3. `seiribu-editorial/strategy/revenue-pages.md` — 収益ページ全般の運用ルール。

## 推奨する起動タイミング
本エンジンは、完成した記事に後付けするのではなく、以下のタイミングで分割実行することを推奨します。
- **構成承認後・本文執筆前**: PHASE 1（案件適合とCTA配置計画の策定）
- **本文執筆後**: PHASE 2（挿入テキストの差分作成）
- **公開直前**: PHASE 3（現行ASP条件の再確認と記事ファイル更新）

## 起動方法
`/revenue-engine [対象記事のファイルパス]`
（例：`/revenue-engine seiribu-editorial/drafts/how-to-dispose.md`）

# ⛔ 【最重要：ステートマシン制約】

> [!IMPORTANT]
> 1. **フェーズ宣言**: 出力の冒頭で必ず `【現在実行中のフェーズ: PHASE X】` と宣言すること。
> 2. **スコープ制限**: 指定されたフェーズ以外の内容は出力しないこと。
> 3. **ファイル更新の厳格化**: PHASE 1・2 では**絶対に記事ファイルを更新しない**。提案は `reports/` に保存する。記事ファイルの更新は最終承認後の PHASE 3 のみで行う。
> 4. **強制停止**: 各フェーズの最後は必ずユーザーへの確認で終え、**出力を完全に停止**すること。

# 案件選定・執筆のルール

## 1. 最新性の判定と提携状況チェック（P0）
案件の条件（提携状態、成果地点、対象LPなど）は、古いサマリー情報を鵜呑みにせず、**「現行ASP画面・条件情報 → 現行公式LP → 日付付きローカル資料」**の順で判断すること。
競合する情報や不明な点がある場合はステータスを `要確認` に落とし、ユーザーに最新ASP画面の確認を求める。

## 2. 読者ファーストと案件マッチング（P1）
「ピラー2だから専門買取」というような粗い判定はしない。記事の主KW、読者の決断点、広告の成果対象、LPの親和性を綿密に結びつけること。（例：混在品はバイセル、ブランド品は専門案件、骨董は専門業者など）
`strategy/revenue-pages.md` の「現在は公開導線に使わない案件」は、候補としても自動選定しない。

**【収益化のコア：痛みからの解放とフローチャート式提示】**
- 単に「手間がある」と代弁するだけでなく、「もう限界だ、お金を払ってでもこの苦痛（親戚トラブル・休日のゴミ運び）から抜け出したい」という**読者のペインの限界点を突き、その苦痛を終わらせるチケット（特効薬）として案件を提示する（リフレーミング）**こと。
- 案件提示は「フローチャート思考」を用い、「この痛みから逃れたいならコレ一択」と、読者に考えさせず・選ばせないUXで配置すること。

## 3. CTA配置の制限とトーン＆マナー
- **10秒判断ブロック内のリンク禁止**: 記事冒頭の10秒判断ブロック内には案件リンク（CTA）を置かない。品目別の判断が終わった直後の、読者が行動を決めるタイミングにのみ限定する。
- **広告表記の重複禁止**: WordPress側の自動表記を正とするため、Markdownの本文中や記事末尾に重複して「広告である旨の記述」を追記しない。
- 煽り文句（「絶対おすすめ」「今すぐチェック」）は厳禁。
- 絵文字（⚠️、➡、✅など）は使用しない。

## 4. リンクのプレースホルダー形式
アフィリエイト規定テキストリンクの改変を防ぐため、誠実な案内（地の文）の直後にプレースホルダーを置く。絵文字は使用しない。

```markdown
※具体的な行動を示す誠実な案内文（例：着物の価値を正確に知るために、まずは対象になるか相談してみましょう。）
[ASP規定のテキストリンク・バナー] <!-- CMS: 〇〇のアフィリエイトリンクを挿入 -->
```

# 実行フェーズ

## PHASE 1: 記事の文脈分析と案件マッチング計画

AIの行動:
1. 対象記事の構成案または本文全文を読み込む。
2. `seiribu-affiliate-case-selector` に従い、記事のKWと読者状況に適合する案件を選定する。
3. 以下を評価・確認する。
   - 案件の提携状態・成果地点・対象・否認条件（最新性の裏付けを明記）
   - 記事内のどの文脈（H2/H3）に、どのようなペイン解消のブリッジで配置するか
   - この記事では案件を置かない方が読者に適切か
4. **記事ファイルを直接編集せず**、案件選定とCTA配置計画を `reports/revenue-plan-[記事スラッグ].md` として保存する。

AIの出力:
- 選定した案件と最新性判定の根拠
- 挿入予定箇所とロジック（ブリッジ）
- 案件を置かない場合は、その判断と代替となる内部リンク
- `reports/` へのプラン出力完了報告
- ユーザーへの確認依頼（「このプランで本文執筆またはPHASE 2へ進んでよいですか？」）

ここで完全停止。

---

## PHASE 2: 訴求テキストのドラフト生成

AIの行動:
1. PHASE 1の承認済みプランに基づき、記事へ挿入するテキスト（ブリッジとプレースホルダー）のドラフトを作成する。
2. 以下のセルフチェックを行う。
   - 10秒判断ブロック内にリンクを配置していないか
   - 絵文字を使用していないか
   - 広告表記を重複して追加していないか
   - 案件の否認条件に抵触していないか
3. **記事ファイルを直接編集せず**、テキストの差分案をユーザーに提示するか、`reports/revenue-plan-[記事スラッグ].md` に追記する。

AIの出力:
- 挿入箇所前後の変更前（Before）と変更後（After）の差分（Markdown diff形式）
- ユーザーへの確認依頼（「この差分で公開準備（PHASE 3）に進んでよいですか？」）

ここで完全停止。

---

## PHASE 3: 記事ファイルへの反映と最終監査

AIの行動:
1. ユーザーの最終承認を得た後、ファイル編集ツールを使用して対象の `.md` 記事ファイルを更新する。
2. 更新後、**KW監査と計測記録**を行う。
   - 記事が商業寄りになり検索意図を失っていないか（トーンの崩れ）を監査する。
   - 今回配置した案件の記録（案件名、ASP、プログラムID、LP、確認日、配置箇所）を整理し、Notion案件台帳更新用データとして提示する。

AIの出力:
- 記事の更新完了報告
- KW監査の結果（検索意図が保持されているかの確認）
- Notion案件台帳更新用・実績トラッキング用の記録データ
- 次のアクション提案（公開作業、画像手配など）
