# 記事出力フォーマットルール

記事を `.md` ファイルとして出力する際、以下のフォーマットに従うこと。
目的は「WordPressへのコピペ入稿時に、不要な情報を消す手間をゼロにする」こと。

## ⛔ 最重要ルール

1. **1ファイル＝1記事**。設計用ファイルと入稿用ファイルを分けない。
2. **本文中に「PHASE」「H2-1」等の制作用ラベルを絶対に書かない。**
3. ファイル冒頭のHTMLコメント（凍結済み設計図）は、WordPress上では非表示になるため、消す必要がない。
4. 本文はHTMLコメントの直後から始め、**そのままコピペで入稿できる状態**にすること。

## ファイル構成

```
<!-- === 凍結済み設計図（Invariants） === ... === END === -->

# タイトル（H1）

導入文（「この記事でわかること」の箇条書きまで）

## 最初のH2見出し（番号なし）

（First Answer Rule：ここで読者の検索意図に対するアトミックアンサーを1〜2段落で即答する。その後に詳細説明へ繋げる）

本文...

## 〇〇（ターゲットKW）に関してよくある質問

**質問文**
回答文

## まとめ：〇〇（※見出し内に必ずKWを含めること）

本文...
```

## 凍結済み設計図のフォーマット

HTMLコメント `<!-- === 凍結済み設計図（Invariants） === ... === END === -->` の中に、以下の【】セクションを含めること。

### 必須セクション

```

- メインKW: 
- スラッグ: 
- Meta Description: 
- 記事タイプ: 

【採用タイトル】
（確定したタイトル1本）

【ターゲット読者】
（誰の・どんな悩みを解決するか）

【検索意図】
（読者が何を知りたくて検索しているか）

【Out of Scope（扱わないこと）】

【見出し構成案とインサイト】

  H3: 見出しテキスト

【CTA・導線設計案】

【まとめ設計案】
```

### 任意セクション（必要に応じて追加）
- 【内部リンク設計】
- 【競合との差別化ポイント】
- 【画像設計】

## 本文のルール

### 導入文（読者への愛を動機とした「逆算型PASONA」）

導入文の役割は、**「この記事はまさに自分のためのものだ」と読者に確信させ、本文（H2）へ強く牽引すること**。導入文の中で検索意図への最終回答を出し切ってはならない（答えはH2の直下に置く）。

#### 設計原則

1. **時間軸の精度**：「どこから」と検索している人は、実家に着いてまだ何も手をつけていない「ゼロ地点」にいる。または今まさに圧倒されてスマホを手に取った瞬間にいる。その時間軸に合わせた心の声を代弁する。
2. **心の声は情景の描写**：分析や解説ではなく、「その場で起きていること」をそのまま切り取る。読者が「まさに今の自分だ」と感じる。
3. **KWの視覚化とタメ**：心の声の直後に、読者が検索したKWを自然に文中に出して視覚化する。読者が「そうそう、それで検索したんだよ」と頷く思考のテンポ（タメ）を作ってから次へ進む。
4. **悪いパターンの提示**：どんな大変さが生じるか、多くの人がどんなパターンにはまり込むかを示す。貴重な休日が消耗で終わる、など具体的に。
5. **記事の役割の宣言**：「調べてわかったことを整理してシェアします」というKackyのスタンス（専門家ではなく、同じ立場で調べた案内人）で記事の概要を示す。
6. **Kackyの一言**：記事の対象読者を明確にし、「〜方の参考になれば嬉しいです」という形で締める。ラベルや鉤括弧は出力しない。

#### 禁止事項（すべての記事共通）
- 固定の挨拶文（「こんにちは。〜セイリ部です」）：全記事で**使用禁止**
- `〜はありませんか？`：心理的防御を生む問いかけは厳禁
- `〜という壁です`／`多くの人がぶつかるのが〜`：コンサル・AI特有の偉そうな表現
- `決してあなただけではありません`：過剰な煽り
- `唯一の正解です`：強すぎる断定・押し付け
- `しかしそれは最初の一歩に過ぎません`：LPのような作為的な煽り
- `このように感じるのは〜`／`実はこのようなケースは〜`：AI固定フレーズ
- 「絶望」「絶対に避けるべき」など過剰にドラマチックな表現
- 導入文の中でFirst Answer（検索意図への最終回答）を出し切ること

#### 導入文のフォーマット（全記事共通）

```markdown
「（読者の心の声1：ゼロ地点の情景・状況の描写）」
「（読者の心の声2：喉元まで出ている痛みを代弁）」

（KWの視覚化とタメ：〇〇を前にして「**ターゲットKW**」と途方に暮れてしまう方は少なくありません。と、読者が検索したKWを文中に自然に出して思考のテンポを合わせる）

（情景の続き：実家の荷物は〜など、その場で起きていることを情景として描写する。分析・解説モードにならないこと）

（悪いパターンと記事の役割：順番を決めずに始めると〜貴重な休日が消耗で終わる、という悪いパターンを示し、この記事がそれを回避するためにあることを誠実に伝える）

この記事では、自力で〇〇するための「〜」と「〜」について、調べてわかったことを整理してシェアします。

〇〇をどこから始めればいいか迷っている方の、参考になれば嬉しいです。

**この記事でわかること**
- 箇条書き1
- 箇条書き2
- 箇条書き3
- 箇条書き4
```



### 見出し
- `##` はH2、`###` はH3で出力。番号（①②、H2-1等）は付けない。
- 読者が「何が書いてあるか」をひと目で判断できる見出しにする。

### 太字（Bold）のルール
- **括弧と太字の位置関係**: 鉤括弧「」や丸括弧（）を太字にする場合、`**` は必ず括弧の**内側**に置く。
  - 正：「**テキスト**」
  - 誤：**「テキスト」**
- **強調は最小限に**: 本当に重要な箇所のみ太字にし、乱用しない。
- **自然な文脈に溶け込ませる**: 不自然な鉤括弧囲みは避け、文章の流れの中で太字を使う。

### 内部リンク
- `> **あわせて読みたい：**` の引用ブロック形式で、説明1文＋リンクを配置。

### 本文画像ブリーフ
- **1記事に必要な画像一式**: アイキャッチ1枚 ＋ 記事の内容に応じた十分な数の画像（目安3〜5枚）。
- **図解と情景イラストのバランス**: B2B向けのコンサル資料ではないため、比較表やフローチャートなどの「図解」ばかりに偏らないこと。読者の感情に寄り添い、雰囲気を伝える「情景イラスト」や「写真風素材」のアイデア（例：実家の段ボールの山、笑顔で話し合う親子など）をバランス良く盛り込むこと。
- 記事エージェントは「種類・目的・読者に伝えたい感情・入れたい要素（アイデア）・避けたい表現」までを指定する。完成プロンプト、文字入れ、ロゴ配置、フォント指定は画像制作側またはローカル合成工程に渡す。完成版のセイリ部ロゴは画像制作側で必須配置するため、記事エージェントが個別に指示しなくてよい。
- セイリ部のブランドでは、写真よりも**温かい編集イラスト**が基本。写真風素材は「品物の実物感」が重要な記事に限定する。

#### アイキャッチ画像ブリーフ（必須）
すべての記事に必ず1枚、以下のフォーマットでアイキャッチの制作ブリーフを記述すること。設置位置は記事ファイルの末尾（まとめセクションの後）。
※画像制作エンジンでは文字や背景を含まないイラスト素材を生成するため、テキストの生成や背景の描画を行わないよう明確に指示すること。
```
> [!CMS担当者へ：アイキャッチ画像]
> - 種類：アイキャッチ素材（文字や背景を含まない、人物と小物のイラスト素材のみ）
> - 目的：
> - 読者に伝えたい感情：
> - 構図：
> - 入れたい人物・物：
> - 避けたい表現：画像内へのテキスト（文字）の生成、背景の描画、（その他記事特有のNG表現）
> - タイトル文言：（※画像内には生成せず合成時に追加）
> - サブタイトル文言：（※同上）
> - ALT：
> - ファイル名：
```

#### 本文画像ブリーフ（本文中の該当箇所に配置）
読者の理解を助ける図解や、感情に寄り添う情景イラストを、本文中の該当箇所に引用ブロック形式で配置する。「完成プロンプト」ではなく、画像制作者に意図を伝える「制作ブリーフ」として記述すること。
```
> [!CMS担当者へ：ここに画像を挿入]
> - 種類：記事内イメージ素材 / 写真風素材 / 記事内図解素材 / 図解用小物素材
> - 画像の目的：
> - 読者に伝えたい感情：
> - 画像のアイデア（情景・図解の具体案）：
> - 避けたい表現：画像内へのテキスト（文字）の生成、（その他記事特有のNG表現）
> - ALT：
> - キャプション候補：
```

### FAQ
- H2見出しは単なる「よくある質問」ではなく、必ずターゲットKWを含めること（例：`## 急に物を減らしたくなることに関してよくある質問`）。
- CMS入稿時の削除の手間を省くため、**「Q.」や「A.」といった文字は絶対に出力しないこと。**
- **質問文のテキスト全体を太字にする**。回答文は通常のテキストで書く。
  - 正：`**質問文**`
  - 誤：`Q. **質問文**`
- 構造化データ（schema.org FAQPage）に変換可能な形式を維持。

### 禁止事項
- 本文中に `---`（水平線）を使わない。
- 本文末尾にメタ情報を別途書き出さない（凍結済み設計図に集約する）。
- frontmatter（YAMLの`---`ブロック）は入稿用ファイルには使わない。
